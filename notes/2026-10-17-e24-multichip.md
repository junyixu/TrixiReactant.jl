# 2026-10-17 E24：一台主机上的多个 TPU 芯片（sharding）

单个 v5e 芯片 16 GB HBM：3D FD 在 100 万单元时一个芯片编译不出来。这里用 Reactant 的 sharding 把数组原型分到多个芯片上，
看扩展性和能放多大的网格。

- 脚本：`experiments/e12_p4est_array.jl` 的 `shard` task（砖形路径 `dim,fdloop,faces`）
- 做法：状态和所有带单元维度的数组按**最后一个单元维度**切开（每个芯片一层单元），小数组（算子、单位向量）复制到每个芯片；
  代码不变，XLA 的 SPMD partitioner 自己加上跨芯片面切片的通信（`Sharding.Mesh` + `NamedSharding` / `Replicated`）。
  1 个芯片时用普通（不分片）的数组：1 个设备的分片编译会报 "No sharding found for the output of the loaded executable"
- 机器：GCE 上的 TPU 实例算进 `GPUS_ALL_REGIONS` 配额（项目只有 1），开不了 4 芯片的 `ct5lp-hightpu-4t`，所以用
  Cloud TPU API 的 `v5litepod-4` + Docker 镜像 `:tpu`（和 E14 一样）
- 日志：S3 `2026-10-17-e20-e24/`

## 结果（TPU v5e，Float32，一次 rhs!）

| 网格（单元） | 体积分 | 1 芯片 | 2 芯片 | 4 芯片 | 8 芯片 |
|---|---|---|---|---|---|
| 128×64×32（26 万） | 弱形式 | 38.9 ms | 20.4 ms | **9.69 ms（4.0×）** | 配额不够 |
| 同上 | FD | 55.7 ms | 26.5 ms | **14.1 ms（3.96×）** | |
| 128×128×64（105 万） | 弱形式 | 204 ms | — | 42.6 ms（4.8×） | |
| 同上 | FD | XLA 编译失败（报错只记下了第一行，可能是 HBM 不够） | — | 62.0 ms | |
| 128×128×128（210 万） | 弱形式 | — | — | 89.4 ms | |
| 同上 | FD | — | — | 132.6 ms | |
| 256×128×128（419 万，每个芯片 105 万） | 弱形式 | — | — | XLA 编译失败 | |

- 结果和 1 个芯片逐位相同（max|du − du_1芯片| = 0；26 万单元的弱形式/FD 和 105 万单元的弱形式，其余的没有 1 个芯片的结果可比）
- 线性扩展：芯片之间只交换切开那个方向的一层面数据，相对于每个芯片上的计算很小
- 100 万单元的 FD 一个芯片放不下，4 个芯片可以；4 个芯片上 210 万单元的时间正好是 105 万的 2 倍（线性）
- 容量：每个芯片大约 50 万单元（n = 4，Float32）能稳定编译和运行，100 万单元/芯片时编译失败（弱形式 1 个芯片 100 万还行）。
  419 万单元时主机内存（188 GB）也快用完了：Trixi 在 CPU 上用 Float64 建 semidiscretization
- 8 个芯片：Cloud TPU API 的配额 `TPUV5sLitepodServingPerProjectPerZoneForTPUAPI` 是每个 zone 4 个 v5e 芯片，开不了 `v5litepod-8`

## 结论

- 多芯片不需要改代码：数组原型加上 sharding 注解，XLA 自己做区域分解和通信，扩展接近线性
- 更大的问题按芯片数分（每个芯片大约 50 万单元）；要更多芯片需要申请配额
