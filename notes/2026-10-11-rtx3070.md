# 2026-10-11 RTX 3070 实验记录

RunPod community pod，RTX 3070 8 GB，驱动 575.57.08（CUDA 12.9）。镜像 `runpod/base:1.0.2-ubuntu2404`，
现场安装：Julia 1.12.6，Reactant 0.2.291（Reactant_jll 0.0.416），CUDA.jl 6.2.2，KernelAbstractions 0.9.44，
Trixi 0.17.14（`backend = "kernelabstractions"`, `loop_vectorization = false`）。

## E1 `experiments/e1_basics.jl`：设备与精度

| 后端 | 类型 | axpy, n = 2^24 | sin/cos 归约 |
|---|---|---|---|
| GPU | Float32 | 0.660 ms（305 GB/s） | 0.306 ms |
| GPU | Float64 | 1.216 ms（331 GB/s） | 5.172 ms |
| CPU | Float32 | 5.130 ms | 1.160 ms |
| CPU | Float64 | 9.386 ms | 3.479 ms |

3070 上计算密集算子 Float64 比 Float32 慢约 17 倍。

## E2 `experiments/e2_dg1d_cuda.jl`：TrixiCUDA 风格的 CUDA.jl kernel

1D DGSEM，Burgers，LLF，周期边界，polydeg 3，5 级低存储 RK（CarpenterKennedy2N54）共 100 步。
时间循环用 `@trace for` 编译成一个 XLA 程序。误差相对于**同精度**的 CPU 参考解。

| 模式 | 16384 单元 F32 | 16384 F64 | 1048576 单元 F32 | CPU 后端 16384 F32 |
|---|---|---|---|---|
| 原生 CUDA.jl | 17.2 ms | 17.2 ms | 256 ms | — |
| Reactant，不 raise（3 个 PTX `custom_call`） | 9.9 ms | 13.7 ms | 252 ms | 7006 ms |
| Reactant，raise（80 个 StableHLO op） | 3.1 ms | 12.5 ms | 413 ms | 79 ms |
| raise + shared memory / `sync_threads` kernel | 失败 | 失败 | 失败 | 失败 |

- 能跑的模式，100 步后的解都和 CPU 同精度参考解逐位一致（max|u_T − u0| ≈ 1e-3，确认解在演化）。
- shared memory kernel：`failed to raise func ... volume_kernel_shmem`，GPU 和 CPU 后端都一样。
  它的计时没有参考价值（每个 block 只放 1 个单元、4 个线程）。
- CPU 后端不 raise 也能跑：Reactant 把 kernel 降成 CPU 代码，但比 raise 慢约 90 倍。

已知问题：

- 测试问题条件数差：光滑解加细网格，`invJ` 大，rhs 严重相消。Float32 和 Float64 的 rhs 相对误差
  在 16384 单元为 1e-2，1048576 单元为 0.58。
- 第一个 `reactant_noraise` 模式中单次 rhs 与 CPU 有差异（1e-2 / 0.42），但完整轨迹逐位一致，原因未查。
- CPU 后端 raise 只是 TPU 的代理，没有覆盖 TPU 特有问题（`dot_general` 默认 bf16、libtpu、无 Float64）。

## E3 `experiments/e3_trixi_reactant.jl`：上游 Trixi（P4est 2D，KA）

未跑到 `rhs!`。依次遇到：

1. `wrap_array` 用 `unsafe_wrap(pointer(u_ode))` → `reactant_overrides.jl` 里改为 `ReshapedArray`
2. 容器 `adapt_structure` 用 `unsafe_wrap_or_alloc`（`pointer`）→ 改为拷贝加 reshape
3. `Vector{Tuple{Symbol,Symbol}}` 无法放到设备上 → 留在 host
4. **当前卡点**：interfaces 的 `node_indices` 在 kernel 内传给用 `===` 比较 Symbol 的 helper
   （`index_to_start_step_2d`、`indices2direction`）。CUDA 上能跑是因为 CuArray 存的是 Symbol 指针。

另外，Trixi 的 3D GPU volume kernel 用了 `@localmem` / `@synchronize`，按 E2 的结果大概率无法 raise。
