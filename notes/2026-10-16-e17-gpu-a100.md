# 2026-10-16 E17：A100 上数组原型对 Trixi 原生 CUDA；不经过 Reactant 改 KA kernel 行不行

2026-10-16 计划的第 6 项。两个问题：(1) 数组原型（E12 的代码，Reactant 编译到 CUDA）在 GPU 上是不是也不差——做 package
extension 之前要知道；(2) 导师问"能不能不靠 Reactant、直接改 KA kernel 达到同样性能"：E11 里节点循环展开的
FullSweepGlobal raise 之后比不 raise 的原 kernel 还快（L4，64 单元），这里在 26 万单元上直接用 KA 跑（没有 Reactant）。

- 机器：RunPod Community **A100-SXM4-80GB**（$1.39/h，约 25 分钟），`:latest` 镜像
- 算例：E12 的 `cart32` = P4est 3D `elixir_euler_source_terms_nonperiodic.jl`，32³ 棵树加密一次，**262144 单元**，
  n = 4（1677 万 DOF），LLF + `max_abs_speed_naive`，Kennedy–Gruber，Float32
- 脚本：`experiments/e17_gpu_kernels.jl`（Trixi 原生）、`experiments/e12_p4est_array.jl gpu bench|loops`（数组原型）
- 日志：S3 `2026-10-16-e17-a100/`（本地 `logs/` 同名目录）

## Trixi 原生 CUDA（KernelAbstractions，CuArray）

| | 时间 |
|---|---|
| rhs!，弱形式 | 36.0 ms |
| rhs!，FD（默认 kernel = HalfSweep） | 6.5 ms |
| 参考：E9（周期 64³ 网格） | 34.8 / 5.2 ms |

只算 FD 体积分（`calc_volume_integral!`，同样的输入；和 HalfSweep 的结果差 ≤ 2.6e-7）：

| kernel | 时间 |
|---|---|
| Trixi HalfSweep（shared memory，每对节点算一次） | **2.11 ms** |
| Trixi FullSweep（shared memory） | 3.12 ms |
| Trixi FullSweepGlobal（没有 shared memory，workgroup 动态） | 3.95 ms |
| FullSweepGlobal 的副本，原循环，workgroup 动态 / (4,4,4,1) | 4.09 / 3.26 ms |
| 副本，**节点循环展开**（E11），workgroup 动态 / (4,4,4,1) / (4,4,4,4) | **26.4 / 28.7 / 27.7 ms** |
| 同上，`unsafe_indices = true`，(4,4,4,1) / (4,4,4,4) | 29.0 / 27.7 ms |

- **展开节点循环在原生 CUDA 上慢 7–9 倍**。E11 里展开是为了让 Reactant raise 时没有 gather（循环变量变成下标就是 gather）；
  不经过 Reactant 时它只是把 3 × 4 次 5 分量的两点通量全部摊开，寄存器压力大得多。静态 workgroup 对原循环有一点帮助（4.1 → 3.3 ms）
- 所以对导师问题的回答：**在 GPU 上，"直接改 KA kernel"的方向不是 E11 那种改法**——Trixi 现有的 FD kernel（HalfSweep）已经很快；
  慢的是弱形式（36 ms，E10：78–85% 时间在每个单元一个线程的通用体积分 kernel），那里该做的是每个节点一个线程的弱形式 kernel。
  在 TPU 上根本没有不经过 Reactant 的 KA 路径

## 数组原型（Reactant → CUDA，同一个 A100）

| 选项 | rhs! 弱形式 | rhs! FD | 一个 RK 步 |
|---|---|---|---|
| base（gather 路径） | 14.8 ms | 14.7 ms | 弱 `trace` 93.7 ms（1.26 × 5 rhs!） |
| `dim,fdloop,faces`（TPU 上最快的组合） | **12.9 ms** | 24.4 ms | 弱 `trace` 360 ms（5.6 ×） |
| `an,dim,fdloop,faces` | 13.0 ms | 19.4 ms | 弱 `hoststage` **67.1 ms（1.03 ×）**；FD `hostrhs` **98.9 ms（1.02 ×）**、`hoststage` 107.6（1.11 ×）、**`hoststep` 590 ms（6.1 ×）** |

- **弱形式：数组原型比 Trixi 原生快 2.8 倍**（12.9 vs 36.0 ms）；**FD：慢 2.3 倍**（最好 14.7 vs 6.5 ms）。和 E9 笛卡尔数组写法
  （12.9 / 9.2 vs 34.8 / 5.2 ms）是同一个格局：P4est 的通用写法在 GPU 上没有额外代价（GPU 的 gather 便宜，E6）
- TPU 上调出来的选项在 GPU 上不一定好：`fdloop`/`dim` 让 FD 从 14.7 变成 24.4 ms；`trace` 循环在 GPU 上也很差
- E14 的结论在 GPU 上同样成立：**整个 FD 的 RK 步放进一个程序慢 6 倍**，每个阶段一个程序就正常 —— 这是 XLA 的问题，不只是 TPU 的
- 和 TPU v5e 比（E12/E14 的最好结果）：rhs! 38.9 / 55.7 ms，RK 步 197 / 283 ms；A100 上数组原型 RK 步约 67 / 99 ms，
  Trixi 原生 RK 步约 5 × 36.0 / 5 × 6.5 ≈ 180 / 33 ms（只算 rhs!）

## 结论

- 数组写法在 GPU 上也站得住：弱形式明显快过 Trixi 现在的 kernel，FD 慢 2.3 倍（Trixi 的 HalfSweep 用 shared memory 只算一半的两点通量）
- 做 package extension 时 GPU 和 TPU 要用不同的选项（布局、`fdloop`），时间循环都用"每个阶段一个程序"
- "直接改 KA kernel"：E11 的展开只对 Reactant raise 有用，原生跑反而慢 7–9 倍；原生方向上该改的是弱形式的体积分 kernel
