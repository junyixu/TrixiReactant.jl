# 2026-10-15 E12：3D P4estMesh 上的数组写法原型

导师 2026-10-13 批准走数组路线（先做独立原型，`P4estMesh`，3D 更重要，Float32，算例参考 GPU 测试）。
E7/E9 只能做笛卡尔网格（邻居靠切片）；E12 接受 Trixi 半离散化里的任意**协调**（没有 mortar）`P4estMesh`。

- 脚本：`experiments/e12_p4est_array.jl`（`check` 对比 Trixi 的 rhs!，`bench` 计时；`E12_ABLATE=nogather` 把
  邻居 gather 换成自己的面，用来量 gather 的开销）
- 机器：GCP TPU v5e-1（us-west4-a，按需），`:tpu` 镜像；check 先在同一台 VM 的 CPU 后端上跑（容器不加
  `--privileged`，看不到 TPU，不影响同时跑的 TPU 任务）
- 日志：S3 `2026-10-15-p4est-array/`

## 做法

- **物理部分直接用 Trixi 自己的逐点函数**：`flux`、两点体积通量（`flux_kennedy_gruber`）、面通量
  （`FluxLaxFriedrichs(max_abs_speed_naive)`）、Dirichlet 边界值、源项，都通过对数组 broadcast 调用，
  Reactant 把标量函数追踪一次、生成逐元素的运算。所以换方程不用重写通量（只测了可压 Euler 3D）
- **DG 算子是数组运算**，状态是每个变量一个 `(n, n, n, 单元数)` 数组，单元顺序和 Trixi 一样：
  - 体积分：弱形式 = 逆变通量 $\tilde f^d = \sum_j Ja^d_j f_j$ 沿第 d 个节点维度乘 `derivative_hat`；
    flux differencing = 沿每个维度所有节点对的两点通量（法向量取两点 $Ja^d$ 的平均）乘 `derivative_split` 求和
  - 面：每个单元 6 个面（"slot"）。自己的面值靠切片；**邻居的面值靠一次 gather**：从
    [所有单元的面; Dirichlet 边界值] 里按下标取整块面（所有变量 × n×n 个节点），再按 8 种面朝向之一翻转/转置；
    每个 slot 用 Trixi 主单元的外法向算数值通量。每个界面的通量两边各算一次（不需要 scatter），
    和 Trixi 只差符号，按位一样
  - 网格信息（逆变向量、Jacobian、法向量、gather 下标、朝向）在 CPU 上从 Trixi 的 cache 里一次性取出，
    照着 Trixi 的 "delayed indexing" 循环算，并断言和面积分用的面节点编号一致
- 为了让 Trixi 的逐点函数能追踪，加了三个方法：`Trixi.sqrt`/`Trixi.log` 对 traced 标量用 Base 的（Trixi 的只定义在
  `Real` 上），以及 Reactant 的 `norm` overlay 对 `SVector` 的回退（它把 `SVector` 当 XLA 数组做 dot，会报错）

## 正确性（和 Trixi 的 rhs! 比，t = 0.3 的精确解处，max|du − du_Trixi| / max|du_Trixi|）

| 算例 | 网格 | 体积分 | Float64 | Float32 |
|---|---|---|---|---|
| `elixir_euler_source_terms_nonperiodic.jl`（GPU 测试的算例） | 2×2×2 树，64 单元，n = 4，96 个边界面 | 弱形式 | 1.3e-13 | 4.1e-5 |
| 同上 | 同上 | flux differencing | 1.3e-13 | 5.6e-5 |
| `elixir_euler_source_terms_nonperiodic_hohqmesh.jl` | 弯曲非结构网格，204 单元，n = 5，4 种命名边界；96 个面需要翻转 | 弱形式 | 1.4e-13 | 7.3e-5 |
| 同上 | 同上 | flux differencing | 2.1e-13 | 1.0e-4 |

Float32 的误差是 Float32 舍入的量级（E7 也是 ~1e-5）。

在 TPU 上（Float64 是软件模拟）同样对：cart2 2.2e-12 / 3.4e-12，hohq 3.7e-12 / 7.1e-12（Float64，弱形式 / flux
differencing），Float32 4e-5 – 1.3e-4。

## 性能：第一版（base）

TPU v5e，Float32，`cart<T>` = T×T×T 树、加密 1 层：

| 网格 | 单元数 | 节点数 | rhs! 弱形式 | rhs! flux differencing | 编译 rhs! |
|---|---|---|---|---|---|
| cart8 | 4096 | 26 万 | 2.42 ms | 2.45 ms | 21–94 s |
| cart16 | 32768 | 210 万 | 26.4 ms（12.6 ns/节点） | 26.7 ms | 43 s |
| cart32 | 262144 | 1677 万 | 251 ms（15 ns/节点） | — | 292 s |

- 比 E9（笛卡尔、切片）慢 4–6 倍/节点；弱形式和 flux differencing 一样慢，说明时间不在体积分
- 26 万单元时 RK 时间循环编译不出来：HLO 临时数组 18.7–30 GB，v5e 只有 15.75 GB HBM
- cart32 第一次跑时进程段错误，是脚本的 bug：`Trixi.wrap_array` 是 `unsafe_wrap`，没有 `GC.@preserve`
  底层向量，大数组拷贝时被 GC 回收了

**profile**（cart16，`tools/profile_summary.py`，每次 rhs!）：

| 类别 | 时间 | 占比 | 读写量 | 带宽 | kernel 数 |
|---|---|---|---|---|---|
| 逐元素 | 16.6 ms | 64% | 2.3 GB | 139 GB/s | ~400 |
| 转置/拷贝 | 7.6 ms | 29% | 0.9 GB | 119 GB/s | 80 |
| 矩阵乘 | 1.2 ms | 5% | 0.7 GB | 594 GB/s | 15 |
| gather | 0.36 ms | 1.4% | 0.12 GB | 331 GB/s | 1 |

合计约 97 个状态大小的读写（E9 是 7–11 个）。gather 本身很便宜；贵的是它前后的布局转换：
面数组 `f32[32768,6,5,4,4]{1,0,4,3,2:T(8,128)}` 把长度 6 的面维度放在最内层（每个 128 宽的块大部分是空的），
拷进拷出各 2 ms、只有 58 GB/s，另外还有约 20 个 0.39 ms、60 GB/s 的拷贝。
去掉 gather 的对照（`E12_ABLATE=nogather`，结果不对，只量开销）：cart16 弱形式 15.9 ms（有 gather 时 26.2 ms），
cart32 141 ms（251 ms）。

## 优化（导师/用户 2026-10-15 给的 6 条思路，逐条累加试）

`E12_OPTS` 开关，每一步在 TPU 上 bench（32k / 26 万单元）并 profile：

| 版本 | 内容 |
|---|---|
| base | 第一版 |
| v1 | `dim`：沿节点维度的导数写成 n 个切片项（不再 `permutedims` → 矩阵乘 → `permutedims`） |
| v2 | + `fdloop`：flux differencing 写成对 ii 的求和 `D_split[:, ii] .* f(u, u_ii)`，不生成节点对数组 |
| v3 | + `faces`：砖形网格（所有面朝向都是恒等）按面的连接关系排成全局 (Nx, Ny, Nz)，面通量直接从切片算，边界层用 `pad` 加上（没有 gather、没有拼接） |
| v4 | 同 v3，网格换成最长维度 128（128×16×16 / 128×64×32 个单元） |
| v6 | + `step`：RK 每个阶段直接用 rhs! 的结果更新 K、U，时间循环里不再带 `dU` |
| v5 | `trees`：均匀加密网格每棵树是 (m, m, m) 块，树内面用切片，树之间一次 gather 取整个树面（含朝向），适用于非结构网格 |

另外加了一项（profile 之后想到的）：`an` = Trixi 的逐点函数在整个数组上只调用一次、一次得到所有分量
（`AN{T} <: Number` 包一个数组，标量运算变成 broadcast），而不是每个分量一个 broadcast（担心 XLA 没把 5 次
重复的通量计算合并）。

所有开关组合都和 Trixi 的 rhs! 对过（CPU 后端，Float64 ≤ 4.2e-13，Float32 ≤ 2.8e-4）：`dim,fdloop` 在
cart2/hohq 上，`faces` 在 cart2 上，`trees` 在 cart2、cart1_2（1 棵树 4³）、hohq_1（弯曲非结构网格加密 1 层，
204 棵树各 2³ 个单元，96 个树面要翻转）上，`an` 在 cart2/hohq_1 上。

TPU v5e，Float32，rhs! 时间（ms），括号里是一个 RK 步（5 次 rhs!）：

| 版本 | 32768 单元 弱形式 | 32768 单元 FD | 262144 单元 弱形式 | 262144 单元 FD |
|---|---|---|---|---|
| base | 26.2 (303) | 26.5 (300) | 251（循环放不进 HBM） | — |
| v1 dim | 25.6 (114) | 26.5 (126) | | |
| v2 + fdloop | 25.6 (114) | 26.9 (134) | 253（循环 16.2 GB，放不进） | |
| v3 + faces | 14.2 (65) | 24.4 (621，循环编译 1470 s) | 69.7 (325) | 112（循环编译超过 1 h，被停掉） |
| v4 同 v3，单元 128×16×16 / 128×64×32 | **2.79** (120) | **4.81**（1234，循环编译 1917 s） | **38.9** (300) | **55.7**（循环编译太久，停掉） |

- v1、v2 几乎没变：瓶颈在面那一块（slot 数组的布局转换）和几百个小 kernel，不在转置或节点对数组
- v3 把面的 gather/拼接去掉以后，弱形式快了 1.8 倍（32k）/ 3.6 倍（26 万）
- v3 的 FD 时间循环编译了 1470 s，每步 621 ms（比 5 次 rhs! 慢 5 倍）：展开的 FD 放进 traced 循环后 XLA 处理得很差
- v3 的 profile（cart16）：弱形式 76 个状态大小的读写（base 97），FD 105 个；最大的几个 kernel 只有 113–137 GB/s、
  170–200 GFLOP/s，两样都远低于上限。HLO 里状态的布局是 `f32[32,32,32,4,4,4]{2,5,4,3,1,0:T(4,128)}`：
  XLA 把一个长 32 的单元维度放在最内层，TPU 按 128 分块，**每个数组补齐 4 倍**（面切片也一样）——正是第 4 条
- **v4 只把网格换成最长维度 128（单元数不变）就快了 5 倍**：32k 单元弱形式 2.79 ms（1.33 ns/节点）、
  FD 4.81 ms（2.29 ns/节点），接近 E9 在 128 友好网格上的 1.1–1.4 ns/节点；26 万单元快 1.8–2 倍（38.9 / 55.7 ms，
  E9 同样的 128×64×32 网格是 18.9 / 22.7 ms，还差 2 倍）。时间循环没跟着变快（弱形式一步 120 ms，5 次 rhs! 才 14 ms），
  FD 的循环编译 30 分钟以上

| v6 + step | 2.79 (119) | 4.79 (1234，循环编译 1943 s) | 38.9 (298) | 55.7 |

- **v6（第 6 条）没有效果**：时间循环里不带 `dU` 之后每步时间完全一样
- **时间循环慢的原因是布局**（循环的 profile + HLO，`E12_PROFILE_LOOP=1`）：单独一次 rhs! 里 XLA 给状态选的是
  `f32[4,4,4,128,16,16]` 的 `{3,5,4,2,1,0}`（长 128 的维度在最内层），而 while 循环里用的是默认的
  `{5,4,3,2,1,0}`——**最后一个维度**（长 16）在最内层，补齐 8 倍；循环里几百个 `multiply_add` kernel 只有 ~90 GB/s
  （单独 rhs! 里是 1 TB/s 以上的等效带宽）。所以 2 步 242.6 ms = 每步 121 ms，而 5 次单独的 rhs! 才 14 ms
- 推论：要让**最后一个**维度是 128 的倍数（循环外 XLA 自己选布局，循环里用默认布局）。验证：同样 32768 个单元排成
  16×16×128（128 在最后），循环里布局变成 `{5,3,4,2,1,0}`、最内层是 128，**2 步 50.1 ms = 每步 25 ms**
  （128 在最前时每步 121 ms），正好是 5 次 rhs!。但单独一次 rhs! 反而慢了（4.86 ms，128 在最前时 2.79 ms）：
  XLA 在两种情况下选的次内层维度和面切片的方向不同

| v6 + step，单元 16×16×128 / 32×64×128（128 在最后） | 4.86 (**24.2**) | 8.30 (**162**，循环编译 701 s) | 55.0 (**230**) | 91.8 |

- 128 放在最后：单独的 rhs! 慢一些，但**时间步快了 1.3–7.6 倍**（每步 24.2 / 162 / 230 ms，128 在最前时 119 / 1234 / 298 ms）。
  FD 的循环还是比 5 次 rhs! 慢 4 倍，编译也还要 12 分钟

| v7 + an（128 在最后） | 4.88 (24.2) | 7.75 (156，循环编译 746 s) | 55.0 (230) | **75.0** |

- `an` 对弱形式没影响，FD 快 7%（32k）/ 18%（26 万）：XLA 本来就把 5 个分量里重复的通量计算大部分合并了，
  我原先的猜测（每个两点通量算 5 遍）基本不对

**树分块（第 5 条，`trees`）**：每棵树 4³ 个单元，树维度在最后（512 / 4096 棵树）：

| 版本 | 32768 单元 弱形式 | 32768 单元 FD | 262144 单元 弱形式 |
|---|---|---|---|
| v5 trees + step | 27.8 (164) | 43.2 (209) | 305（循环编译时被容器 28 GB 内存上限杀掉） |
| v8 + an | 27.8 (164) | 38.4 | （同上） |

- 树分块**按现在的写法更慢**（和第一版的 gather 差不多甚至更差）。profile：状态本身的布局没问题
  （`f32[512,4,4,4,4,4,4]{0,…}`，树维度在最内层），时间花在把每个树面重排成 (n m, n m, 树数) 的拷贝上
  （每个 ~2 ms、35–38 GB/s），逐元素和转置 kernel 也只有 ~100 GB/s；94–122 个状态大小的读写
- 要让树分块划算，得换一种不需要重排树面的表示（例如让树面数组直接以树维度为最内层，或者把树维度和一个单元维度合并成 128 的倍数）
- FD 的时间循环在这条路径上编译只要 174 s（结构网格路径要 12–32 分钟）

**非结构弯曲网格**（hohq 加密 2 / 3 层，polydeg 4，`an,dim,fdloop,step`），gather 路径对比树分块：

| 网格 | 路径 | 弱形式 rhs!（一步） | FD rhs! |
|---|---|---|---|
| hohq_2，13056 单元 | gather | **17.3 ms**（78.5） | **20.7 ms** |
| hohq_2 | 树分块（每棵树 4³） | 23.2 ms（142） | 36.4 ms |
| hohq_3，104448 单元 | gather | 164 ms（循环编译时被内存上限杀掉） | — |
| hohq_3 | 树分块（每棵树 8³） | **118 ms**（868） | 191 ms |

- 树大一些（8³）时树分块的 rhs! 比 gather 快 1.4 倍，小树（4³）时更慢；时间循环在这条路径上都很差（树维度 204 在最后，补齐到 256，
  加上树面重排）

## 总结（6 条思路逐条试的结果）

26 万单元（1677 万节点）、TPU v5e、Float32，rhs!（时间步）：

| | 弱形式 | FD |
|---|---|---|
| base | 251 ms（循环放不进 HBM） | — |
| 最好（v4，单元 128×64×32） | 38.9 ms（一步 298） | 55.7 ms |
| 最好的时间步（v7，单元 32×64×128，128 在最后） | 55.0 ms（**一步 230**） | 75.0 ms |
| 参考：E9 笛卡尔、同样网格 128×64×32 | 18.9 ms | 22.7 ms |
| 参考：A100 上 Trixi 原生 CUDA（E8，64³） | 34.8 ms | 5.2 ms（HalfSweep） |

| 思路 | 结果 |
|---|---|
| 1. 小矩阵乘展开（`dim`） | rhs! 几乎不变（这里瓶颈不在转置）；时间循环快了 2.7 倍 |
| 2. FD 不生成节点对数组（`fdloop`） | 几乎不变；配合 `an` 后 FD 快 7–18% |
| 3. 面通量直接从切片算（`faces`，砖形网格） | **1.8–3.6 倍**：去掉 slot 数组的布局转换 |
| 4. 布局：128 的倍数 | **最大的一项**：rhs! 再快 1.8–5 倍；时间循环里 XLA 用默认布局，所以要把 128 的倍数放在**最后一个**维度，否则循环里补齐 8 倍（每步 121 ms → 25 ms） |
| 5. 按树分块（`trees`） | 正确（含非结构弯曲网格的树面翻转），但按现在的写法更慢：树面重排成 (n m, n m, 树数) 是 38 GB/s 的拷贝 |
| 6. 融合时间步（`step`） | 没有效果（慢的原因是布局，不是 `dU`） |
| 另：`an`（逐点函数一次算所有分量） | 弱形式不变，FD 快 7–18% |

- 最好的版本每次 rhs! 仍然读写 78–110 个状态大小的数组（理论上约 2.5 个）：几百个小 kernel、150–190 个转置。
  E11 raise 出来的 FullSweepGlobal kernel 也是 ~100 遍，同一个量级——这是现在这种写法在 XLA 里的上限
- FD 的时间循环编译很慢（结构网格 12–32 分钟，树分块 3 分钟），每步也比 5 次 rhs! 慢 4 倍，原因没查清
- 没做：手写 TPU kernel（Pallas）。Reactant 的 PythonCall 扩展可以在 trace 里调用 JAX 函数
  （`jax.jit(f).lower` → StableHLO → `Ops.hlo_call` 内联，`ext/ReactantPythonCallExt/pycall.jl`），Pallas kernel 在 JAX 里
  lower 成 `stablehlo.custom_call @tpu_custom_call`，所以原则上可以嵌进来；需要镜像里装 Python + JAX(TPU) + PythonCall，没试
