# 2026-10-13 E10：E7/E9 的时间花在哪（profile 和三个验证实验）

E7/E9 给出了运行时间，但原因只是推测。这一轮用 profile 和对照实验逐条检验：

- TPU：Cloud TPU v5e 1 芯片，**按需，us-west4-a**（europe-west4-b 的 Spot 开出来约 10 分钟就被抢占，
  europe-west4-a/b、us-central1-a 都没有按需容量）；日志 `logs/2026-10-13-tpu-v5e-profile/`
- GPU：RunPod **Secure** A100 SXM 80 GB（US-WA-1，$1.79/h，驱动 595；Community 没货）；
  日志 S3 `2026-10-13-a100-profile/`（本地同名目录）
- 新增：E7/E9 的 `fdsym` 体积分（每个无序节点对只算一次两点通量）和 `profile` 任务
  （`Reactant.@profile` + `@code_xla` 优化后的 HLO）；E9 支持非立方网格（如 `128x64x32`）；
  E8 的 `profile` 参数（`CUDA.@profile` 列出 Trixi 每个 kernel 的时间）；
  `tools/profile_summary.py` 把 profile 按类别（矩阵乘、转置、拼接、归约、逐元素、sin/cos）
  汇总时间和读写量（TPU 的 kernel 叫 `fusion.N`，按 HLO 里融合的算子分类）
- `fdsym` 和 Trixi 逐点一致（Float64：2D 1.5e-12、3D 2.9e-11，CPU 和 A100 都查过）
- 注意：profile 的表格要 `COLUMNS=400 LINES=2000`，否则 PrettyTables 按 80 列截断

所有时间都是 Float32、一次 rhs!、1677 万节点。"读写量"= 每个 kernel 的自身时间 × 带宽，
"状态遍数"= 读写量 / 一个状态的大小（2D 268 MB，3D 336 MB）。最少需要约 2.5 遍
（读 U 和坐标、写 dU）。

## 1. Trixi 原生 CUDA（A100）：时间在每单元一个线程的体积分 kernel

| `CUDA.@profile`，每次 rhs! | 总时间 | 体积分 kernel | 清零 du | 界面 | 面积分 + Jacobian + 源项 |
|---|---|---|---|---|---|
| 2D 弱形式 | 16.5 ms | **13.6 ms（83%）** | 1.2 | 0.7 | 0.6 |
| 2D flux differencing | 14.0 ms | **10.9 ms（78%）** | 1.2 | 0.7 | 0.6 |
| 3D 弱形式 | 34.8 ms | **29.5 ms（85%）** | 2.1 | 2.0 | 1.0 |
| 3D flux differencing（HalfSweep） | 6.4 ms | 2.1 ms | — | 2.0 | 1.0 |

- 源码（v0.17.14）：2D 的两种体积分和 3D 弱形式都用通用的 `volume_integral_KAkernel!`，
  `ndrange = nelements`，每个单元一个线程串行跑完整个单元。这一个 kernel 就占 78–85%。
  界面和面积分 kernel 很便宜（2D 合计 1.4 ms）。
- 3D flux differencing 默认用 `HalfSweep`（每节点一个线程、shared memory、利用对称性）：体积分只要 2.1 ms。
- 3D flux differencing 这次是 6.4 ms（E8 那次 5.2 ms，换了机器和驱动；kernel 时间加起来 5.1 ms）。

## 2. A100 上的数组写法：处处受带宽限制，读写量是最少的 7–11 倍

| A100 | rhs! | 读写量（状态遍数） | 主要开销 |
|---|---|---|---|
| 2D 弱形式 | 5.6 ms | 6.2 GB（23） | 8 个矩阵乘 kernel 只跑到 551 GB/s，共 1.8 ms；转置 1.2 ms；拼接 0.9 ms |
| 2D flux differencing | 3.7 ms | 5.0 GB（19） | 融合后的逐元素 kernel 2.8 ms，1.4 TB/s |
| 3D 弱形式 | 14.0 ms | 12.9 GB（39） | **转置 7.2 ms（52%）**，只有 871 GB/s；矩阵乘 3.3 ms |
| 3D flux differencing | 9.2 ms | 9.3 GB（28） | 逐元素 4.1 ms；**转置 3.8 ms**；拼接 1.3 ms |

- 逐元素 kernel 跑到 1.4–1.6 TB/s（峰值 2.0 TB/s 的 70–80%），所以时间 ≈ 读写量 / 带宽。
- 弱形式比 flux differencing 慢的原因：n = 4 的小矩阵乘被拆成单独的 GEMM（551 GB/s），
  y、z 方向前后还要转置。flux differencing 全是广播，XLA 融合得更好。

## 3. "少算一半两点通量"不快反慢：`fdsym`

| rhs! | 2D fd / fdsym | 3D fd / fdsym |
|---|---|---|
| A100 | 3.9 / **8.5** ms | 9.4 / **13.6** ms |
| TPU v5e | 13.7 / **20.8** ms | 22.7 / **37.1** ms（128×64×32） |

- `fdsym` 每个节点每个方向只算 1.5 次两点通量（`fd` 是 4 次），但要把配对两端的值用切片拼接成新数组，
  这些拼接会写回内存：A100 2D 读写量从 5.0 涨到 11.3 GB（拼接 4.0 ms）。
- **推翻了之前的解释**：3D flux differencing 比 Trixi 的 HalfSweep 慢 1.8 倍，不是因为多算了一倍通量，
  而是数据搬运：数组写法要 28 遍状态（含 3.8 ms 转置），HalfSweep 把一个单元读进 shared memory 只读一遍。
  在 XLA 里重算比存中间结果便宜。

## 4. TPU 2D：数据量和 A100 一样，但带宽只有一半

| TPU v5e，2D | rhs! | 读写量（状态遍数） | 平均带宽 | 主要开销 |
|---|---|---|---|---|
| 弱形式 | 10.8 ms | 6.1 GB（23） | 567 GB/s | 含矩阵乘的融合 kernel 5.7 ms（427 GB/s，和源项、dU 组装融在一起）；sin/cos 0.8 ms |
| flux differencing | 13.4 ms | 9.7 GB（36） | 723 GB/s | 逐元素 4.9、转置 3.3、归约 3.0、含 sin/cos 的融合 2.2 ms |

- 弱形式的读写量和 A100 几乎一样（6.1 vs 6.2 GB），慢一倍是因为 TPU 的带宽低
  （峰值 819 GB/s，实际平均 567 GB/s；A100 平均 1.1 TB/s）。
- flux differencing 在 TPU 上融合得更少：读写量 9.7 GB，A100 只有 5.0 GB；转置和归约是单独的 kernel。
- 不是算力问题：`dot_general` 精度从 HIGHEST 降到 HIGH 只快 7%（E7）。

## 5. TPU 3D：内存块补齐，换成有 128 长维度的网格就快一倍

优化后的 HLO 里 64³ 网格的数组布局是 `f32[64,64,64,4,4,4]{2,5,4,3,1,0:T(4,128)}`：最内层是长度 64 的
单元维度，而 TPU 按 128 宽分块，**每块一半是空的**。2D 是 `f32[1024,1024,4,4]{1,3,2,0:T(4,128)}`，
最内层长 1024，不浪费。

| TPU v5e，3D，1677 万节点 | 64×64×64 | 128×64×32 | 32×64×128 |
|---|---|---|---|
| 弱形式 rhs! | 37.0 ms | **18.9 ms** | 18.4 ms |
| flux differencing rhs! | 49.2 ms | **22.7 ms** | 22.6 ms |
| 弱形式的读写量 / 平均带宽 | 9.6 GB / 263 GB/s | 9.9 GB / 535 GB/s | — |

- 单元总数和计算量完全相同，读写量也一样，只是带宽翻倍：**确认是补齐造成的**。
  有 128 长的维度后，3D 每个 DOF 比 2D 贵 1.7 倍，和工作量的增长（约 1.9 倍）一致。
- 换算后的对比：TPU 3D flux differencing 22.7 ms，A100 数组写法 9.4 ms（2.4 倍），
  A100 Trixi HalfSweep 5.2–6.4 ms（3.5–4.4 倍，之前算的是 9.4 倍）；
  3D 弱形式 TPU 18.9 ms，比 A100 上 Trixi 的 34.8 ms 还快。
- 对实际应用的含义：非结构网格的单元是一维列表（长度 = 单元数），没有这个问题；
  结构网格要让某个单元维度是 128 的倍数（或者把单元维度合并成一维）。
- `fdsym` 在 64³ 上时间循环编译失败（XLA 编译出错，没查），反正更慢。
- 想用 L=7（128³ 单元，1.34 亿节点）直接测立方网格，但 XLA 编译失败（弱形式的时间循环、`fdsym` 的 rhs!），
  多半是 16 GB HBM 不够；所以只有上面的非立方对照。

## 结论

| 推测（E7/E9 时） | 结果 |
|---|---|
| TPU 2D 的时间花在中间数组的读写上，不是算力 | **确认**：23–36 遍状态，平均 570–720 GB/s |
| TPU 3D 多出的约 1.7 倍是内存块补齐 | **确认**：布局最内层是长 64 的维度；换成 128×64×32 快 2.0–2.2 倍 |
| A100 上弱形式慢是因为矩阵乘和转置 | **确认**：8 个 GEMM 只有 551 GB/s，转置 1.2 ms（3D 7.2 ms） |
| Trixi 每单元一个线程的体积分 kernel 占大头 | **确认**：占 rhs! 的 78–85% |
| 3D flux differencing 比 HalfSweep 慢 1.8 倍是因为多算了一倍通量 | **推翻**：少算一半反而更慢；差距是数据搬运（转置、拼接） |

每个 rhs! 的读写量是最少需要的 7–11 倍（A100 和 TPU 一样），所以数组写法还有很大的优化空间：
减少转置（选好数组维度顺序）、让 XLA 融合更多。
