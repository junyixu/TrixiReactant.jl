# 2026-10-16 E18：数组原型支持 mortar（静态非协调网格）

2026-10-16 计划第 5 项的 (a)：网格固定（不做 AMR），但有非协调的面（一个大面对 4 个小面），验证 mortar 的数组写法。

- 脚本：`experiments/e12_p4est_array.jl`（gather 路径，3D，守恒通量；算例 `advnc`、`eulernc`）
- 机器：同 E14；日志 S3 `2026-10-16-e14-e19-tpu/`

## 上游 Trixi 的 GPU 路径不支持 mortar

镜像里 Trixi 的 preference 是 `backend = "kernelabstractions"`（GPU 路径），它在 mortar 上直接断言
`isempty(eachmortar(dg, cache))`（`dg_2d_gpu.jl`，2D 和 3D 共用）。也就是说**上游 Trixi 现在在 GPU 上跑不了非协调网格**。
参考值只能用 Trixi 默认的 CPU 路径：在 VM 上另建一个环境，`LocalPreferences.toml` 改成 `backend = "polyester"`，
编译缓存放在单独的 depot（`JULIA_DEPOT_PATH=<新 depot>:/opt/julia-depot`），镜像不用改。
坑：这条路径的 cache 里是 `StrideArray` 而不是 `Array`，`Reactant.to_rarray` 不会整体转换它，而是逐个元素追踪
——71 个单元的网格编译了 36 分钟、超过 10 GB 内存被杀；原型现在把所有输入转成普通 `Array`。

## 做法（照 Trixi 的 `prolong2mortars!`、`calc_mortar_flux!`、`mortar_fluxes_to_elements!`）

- **小面**（每个 mortar 4 个，位置 1–4）：邻居值 = 大面换到 mortar 的节点顺序（8 种朝向之一），再按位置做 L2 投影
  $(F_a \otimes F_b)$（$F$ 是 `forward_lower`/`forward_upper`，第一个矩阵作用在 i 上），作为额外的一块拼到 gather 的源后面；
  通量照常按 slot 算（小单元的状态作 u_ll、小单元的外法向），这正是 Trixi 的 mortar 通量
- **大面**：重新算 4 个 mortar 通量（Trixi 的参数顺序：小面状态、投影后的大面、小面法向），反投影
  $(R_a \otimes R_b)$ 求和、乘 −4，换回大面的节点顺序；再用一次 gather 把这些值替换进所有 slot 的通量里
- 每个 mortar 面的通量在两边各算一次（和协调界面一样，不需要 scatter），多了几次 gather（其中一次覆盖所有 slot）
- 朝向码作为类型（`Val`）传入，traced 循环不会把它们变成 traced 数

## 结果

rhs! 对 Trixi 默认（polyester）CPU 路径（t = 0.3 的精确解），max|du − du_Trixi| / max|du_Trixi|：

| 算例 | 网格 | Float64 | Float32 |
|---|---|---|---|
| `elixir_advection_nonconforming.jl` | 71 单元（一个角加密），周期，6 个 mortar | 3.6e-13 | 1.1e-4 |
| `elixir_euler_source_terms_nonconforming_unstructured_curved.jl` 弱形式 | 弯曲非结构，1020 单元，n = 5，Dirichlet，**298 个 mortar**，界面用到 7 种朝向 | 1.7e-12 | 7.0e-4 |
| 同上 FD | 同上 | 2.6e-12 | 1.6e-3 |

完整模拟（这两个 elixir 不接受 `real_type`，Trixi 只有 Float64 参考）：

| 算例 | 精度 / 后端 | 步数 | 对 Trixi CPU Float64（l2 / linf 最大相对差） |
|---|---|---|---|
| 对流 | Float32 / TPU | 14 / 15 | 2.2e-7 / 1.9e-6 |
| Euler 弯曲非结构 弱形式 | Float32 / TPU | 162 / 162 | 1.7e-4 / 2.7e-3（linf 超出 Float32 测试容差） |
| 同上 | **Float64 / CPU 后端** | 162 / 162 | **7.1e-14 / 8.8e-13** |
| Euler 弯曲非结构 FD | Float32 / TPU | 162 / 162 | 8.4e-4 / 3.1e-3（在容差内） |

- Float64 跑 162 步后和 Trixi 差 1e-13，所以 Float32 那一行的 linf 差别只是 Float32 舍入（弯曲网格、n = 5、Jacobian 小的单元
  把舍入放大；Float32 的 rhs! 本身就差 7e-4）。没有 Trixi 的 Float32 参考可比
- 对流少一步：我们的 Float32 时间累加在第 14 步就到了 `tend`（钳到 `tend`），Trixi 的 Float64 要第 15 个很短的步；误差不受影响

## 没做 / 下一步

- 性能没测；mortar 多出的 gather（尤其是覆盖所有 slot 的那一次）在 TPU 上按下标收费（E6），要做快得换成按 mortar 分组的布局
- 非守恒项（MHD）的 mortar、2D 的 mortar 没做
- AMR（第 5 项 (b)）：网格一变就要重新编译（rhs! 编译 10–130 s），需要按容量分档的 padding 才能避免
